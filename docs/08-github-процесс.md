# Сдача через GitHub: ветка, PR, CI, ревью

Репозиторий: `https://github.com/lexxus2019/concurency`

Этот файл — про то, как практика превращается в маленькую команду разработки.
Тема курса не «написать замок», а «договориться о решениях, которые затрагивают чужой код»,
поэтому сдаётся не файл, а смерженный PR с зелёным CI и отзывом соседней тройки.

---

## 1. Один раз: клонирование и настройка

```bat
git clone https://github.com/lexxus2019/concurency.git concurency
cd concurency
mvn -DskipTests package
mvn -pl exchange-server -am test
```

Дальше каждая тройка работает в своей ветке — они уже созданы в репозитории:

```
strategy/sync        strategy/trylock      strategy/locks
strategy/rw          strategy/optimistic   strategy/queue
strategy/semaphore   strategy/deadlock
```

```bat
git switch strategy/trylock
```

Своя фамилия в ветке не обязательна: ветки общие на тройку, спор идёт о содержимом.

---

## 2. Что именно вы делаете в ветке

1. Добавляете класс стратегии в `exchange-server/src/main/java/ru/lab/concurrent/server/engine/<ваш пакет>/`.
   Больше ничего трогать не нужно, чтобы стратегия появилась в реестре и в API:
   Spring соберёт бины, `EngineRegistry` их зарегистрирует по `name()`.
2. Дописываете имя стратегии в `EngineInvariantTest.fullyCleanStrategies()` — если считаете её корректной.
   Это **единственное общее место**, и оно нарочно оставлено: посмотрите вживую, как
   разрешается конфликт в одной строке, когда её правят две ветки.
3. Прогоняете харнес на двух профилях (`default` и `--scenario=hot`) и прикладываете CSV.
4. Оформляете issue по шаблону **«Задание: стратегия синхронизации»** и PR, связанный с ним.

---

## 3. CI — это и есть «definition of done»

Workflow `.github/workflows/ci.yml` считается на `push` в `main` и на любой PR в `main`
(сами `strategy/*` при пуше не гоняются — проверка появляется, когда ты открываешь PR;
можно и вручную через запуск workflow). Делает три вещи:

* `EngineInvariantTest` — инварианты по всем стратегиям (твоя тоже будет в списке);
* `ReadWriteMicroBenchmarkTest` — стоимость замков без HTTP, артефакт `micro-bench.txt`;
* быстрый прогон харнеса в своей JVM, результат — артефакт `out/ci.csv`.

Падение CI означает: стратегия ломает инварианты или не собирается. Никаких
«у меня на машине работает»: ссылка на прогон CI обязательна в PR.

Диффы `ops/s` из CI ни о чём не говорят — раннеры шумные. Для вывода о цене решения
используй замер на своей машине с `--repeat=3`, CI отвечает только за корректность.

---

## 4. Ревью: соседняя тройка, а не преподаватель

PR проверяет команда, которую **не** трогал твой код: например, `strategy/trylock`
ревьюит команда покупателей. Чек-лист — в `PULL_REQUEST_TEMPLATE.md`, содержательно он
совпадает с `docs/04`.

Что ревьюер обязан спросить (по три вопроса на PR):

1. Какой конкретно точкой из `Transactions` ты защищаешь ресурс и что осталось незакрытым?
2. Какую цифру ты заплатил и на каком профиле нагрузки она снята?
3. Если клиент увидит твой `503`/`409` — он знает, что делать? (Если ответа нет — PR не готов.)

---

## 5. Если правите контракт (`exchange-core`)

Нельзя молча добавить поле в DTO или начать отвечать 409 там, где раньше был 200.
Сначала issue по шаблону **RFC: изменение контракта**, согласование с обеими клиентскими
командами, и только потом код. Причина, которую стоит проговаривать вслух: сервер выбирает
стратегию, а контракт диктует, кто платит за отказ, — то есть это решение трёх команд.

---

## 6. Конфликты: чего ждать и как себя вести

Ожидаемые и полезные:

* `EngineInvariantTest.fullyCleanStrategies()` — обе ветки дописали своё имя; разрешается
  объединением списков, это не «чей код важнее».
* `application.yml` — правило: `exchange.strategy` в файле остаётся `none`, переключение
  только через API/аргументы запуска.
* `docs/02-задания.md`, если кто-то дописывает себе пункт — тогда заведите отдельный файл
  на команду вместо правки общего.

Неожиданные — сигнал, что архитектура поехала: если у вас возник конфликт в
`engine/` (две стратегии правят один файл), значит вы положили код не туда или решили
построить универсальную стратегию на двоих. Это обсуждается на защите, а не мержится.

---

## 7. Итог сдачи

Принимается PR, если:

* CI зелёный;
* в issue заполнена таблица «до/после» на двух профилях;
* есть фраза с числом о цене решения;
* есть одобренный review соседней тройки;
* если затрагивался контракт — есть закрытый RFC с согласованием.

Оценка за практику = состояние PR + устный ответ по банку вопросов (`docs/05`).
Красивый код с unanswered «а что будет, если...» — это 3.
