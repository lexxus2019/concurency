# Шпаргалка: механизмы синхронизации в лабе «Биржа»

Держать открытой во время практики. Все ссылки — на реальный код репозитория.
Обозначения: `server/...` = `exchange-server/src/main/java/ru/lab/concurrent/server/...`,
`core/...` = `exchange-core/src/main/java/ru/lab/concurrent/core/...`.

Ключевые файлы, без которых ничего не понять:

- `server/engine/ExchangeEngine.java` — контракт стратегии (name/title/buy/setPrice/cancel/snapshot…).
  Правило из javadoc: конкурентный отказ обязан быть различим — `BUSY` / `CONFLICT` / `OVERLOADED`.
- `server/engine/AbstractEngine.java` — общая часть; `guarded()` / `guardedTx()` — единственный
  «измерительный прибор» лабы: метрики `lockWait` и `hold` в `server/stats/Counters.java`.
- `server/engine/Transactions.java` — бизнес-логика БЕЗ синхронизации, одна на все стратегии.
  Опасные места помечены `// РИСК:`; между шагами «прочитал → проверил → записал» стоят
  hazard-точки `A:read`, `B:check-then-act`, `C:split-transfer`, `D:field-window`
  (`server/model/Hazard.java`), каждая спит `exchange.hazard-micros` мкс.
- `server/model/Book.java` — общее состояние: `ConcurrentHashMap<String, AtomicReference<LotV>>` +
  кошельки `AtomicLong`. `LotV` — immutable record с полем `version` (`server/model/LotV.java`).
- `server/engine/EngineRegistry.java` — DI-реестр стратегий; переключение на живом процессе
  (`POST /api/lab/strategy`). Важный вывод из javadoc: **исправление гонки не исправляет
  испорченные данные** — до `POST /api/lab/reset` нарушения висят в состоянии.
- `core/check/Invariants.java` — оракл правильности: `OVERSELL`, `LOST_UNITS`, `LOST_UPDATE`,
  `MONEY_LOST`, `MONEY_CREATED`, `NEGATIVE_BALANCE`, `STATUS_INCONSISTENT`, `STOCK_LOST`, `STOCK_CREATED`.
- `core/http/RetryPolicy.java` — клиентские повторы: `LAB_DEFAULT` = 6 попыток, backoff 5 мс ×2
  (до 250 мс), джиттер, перечитывание перед повтором.

## 1. Девять стратегий: карта

| 0 | `none` | `server/engine/broken/BrokenEngine.java` | Ничем. `ref.set()` поверх устаревшего чтения | Максимальный «throughput» на испорченных данных | Все: `OVERSELL`, `LOST_UNITS`, `LOST_UPDATE`, `MONEY_LOST`/`MONEY_CREATED`, `STATUS_INCONSISTENT` |

| 5 | `optimistic` | `server/engine/optimistic/OptimisticCasEngine.java` | Никаких замков: `compareAndSet` по immutable `LotV` + цикл `retryLoop` (`exchange.optimistic-retries`, экспоненциальный backoff прямо в цикле) | `conflicts`/`retries` в счётчиках; на горячем лоте — livelock; контракт обязан включать `expectedVersion` | В записанном состоянии чисто; `snapshot()` — унаследованный, без замка: при проверке под нагрузкой возможен `MONEY_LOST` «деньги в полёте» |

| 7 | `semaphore` | `server/engine/limiter/SemaphoreAdmissionEngine.java` | Только ограничение одновременности: `Semaphore(permits, true)`, `tryAcquire(lock-timeout-ms)` → 503 `OVERLOADED` | Иллюзия защиты | **Задание с подвохом**: составная транзакция не атомарна при permits>1 — все нарушения `none`, просто РЕЖЕ. ## 2. Примитивы Java: синтаксис + где живут в лабе

### synchronized (метод / блок / объект-монитор)

```java
class Lot {
    private int stock;
    synchronized void buy(int q) { stock -= q; }      // монитор = this
    void buy2(int q) {
        synchronized (this) { stock -= q; }           // то же самое
    }
    private final Object mon = new Object();
    void buy3(int q) {
        synchronized (mon) { stock -= q; }            // приватный монитор — лучшая форма
    }
}
```

Семантика стратегии `sync`, но в `GlobalSynchronizedEngine` намеренно `ReentrantLock(true)`:
«замок видно как объект» — им можно управлять, ставить таймаут, читать статистику. У
`synchronized` нет ни таймаута, ни прерываемого ожидания — из `synchronized`-deadlock'а не выбраться.

### ReentrantLock: lock / lockInterruptibly / tryLock с таймаутом

```java
ReentrantLock lock = new ReentrantLock(false);
lock.lock();                                     // ждёт вечно, не прерывается
try { /* критическая секция */ } finally { lock.unlock(); }

if (lock.tryLock(40, TimeUnit.MILLISECONDS)) {   // ограничение ожидания -> 503 BUSY
    try { /* ... */ } finally { lock.unlock(); }
} else {
    return Call.fail(503, Call.Reason.BUSY, null);
}
lock.lockInterruptibly();                        // ожидание реагирует на interrupt()
```

Всё это собрано в одном месте — `AbstractEngine.guarded()`: `timeoutMillis <= 0` → `lock()`
(«просто synchronized», отказов нет, очередь видна только в латентности), иначе `tryLock` и честный
503. Реентерабельность: тот же поток может брать замок повторно (счётчик hold count).

### Честность (fair)

`new ReentrantLock(b)` / `new ReentrantReadWriteLock(b)` / `new Semaphore(n, b)`. Честный замок —
FIFO-очередь: меньше starvation, ниже throughput (каждая передача — unpark конкретного потока,
хуже локальность кэша; нечестный позволяет «протаранить» очередь и выиграть гонку на пустом замке).
В лабе: `sync` зафиксирован на `fair=true`, остальные читают `exchange.fair`;
`SemaphoreAdmissionEngine` — всегда честный. Крутите ручку и смотрите p95 в таблице харнеса.

### ReentrantReadWriteLock

```java
ReentrantReadWriteLock rw = new ReentrantReadWriteLock(false);
rw.readLock().lock();                            // читатели параллельно
try { /* GET /api/lots */ } finally { rw.readLock().unlock(); }

if (rw.writeLock().tryLock(40, TimeUnit.MILLISECONDS)) {   // писатель один
    try { /* buy */ } finally { rw.writeLock().unlock(); }
}
```

Две ловушки (обе — в javadoc `ReadWriteEngine`):
1. **readLock НЕ даёт согласованного снимка**: он не мешает писателю менять данные параллельно,
   поэтому `snapshot()` здесь берёт writeLock — иначе «правильная» стратегия отдаёт грязные данные.
2. Нечестный режим: постоянный поток читателей может держать писателя в starvation
   («затарка» writer starvation). Плюс: read→write апгрейд запрещён (deadlock), write→downgrade — ок.
   Read-locks не «разгоняют» запись: при сплошь записывающей нагрузке — только накладные расходы.

### StampedLock — вариант задания со звёздочкой (в лабе НЕ реализован)

```java
private final StampedLock sl = new StampedLock();
long stamp = sl.tryOptimisticRead();             // ничего не блокируем
LotV snap = this.current;                        // читаем поля
if (!sl.validate(stamp)) {                       // была запись между чтением и проверкой?
    stamp = sl.readLock();                       // падаем на блокирующее чтение
    try { snap = this.current; } finally { sl.unlockRead(stamp); }
}
```

Оптимистичное чтение с `validate()` — гибрид `rw` и `optimistic`: читатели вообще не трогают
состояние замка. Минусы: не реентерабелен, нельзя `await`-подобное ожидание, каждый прочитанный
фолд надо валидировать (многополевой снимок без validate — это несогласованные данные). Замена
`rw` на `StampedLock` — естественное «со звёздочкой»: ожидаете рост ops/s на read-share=0.8.

### Semaphore vs Lock

```java
Semaphore permits = new Semaphore(4, true);
if (permits.tryAcquire(40, TimeUnit.MILLISECONDS)) {
    try { /* работа с ресурсом */ } finally { permits.release(); }  // всегда в finally!
}
```

Отличия, которые спрашивают на защите: у семафора **нет владельца** (release() может вызвать
любой поток — отсюда «утечка» permits при забытом finally), он **не реентерабелен**, у него нет
разделения read/write. Он отвечает на вопрос «сколько одновременно», а не «кто эксклюзивно».
Поэтому `SemaphoreAdmissionEngine` корректен только при `permits=1` — и тогда это плохой замок.

### Atomic* / CAS + переменная версии

```java
AtomicReference<LotV> ref = book.lotRef(lotId);
LotV lot = ref.get();                            // читаем «старое»
LotV next = lot.afterBuy(qty);                   // считаем от него (LotV immutable!)
if (!ref.compareAndSet(lot, next))               // пишем, только если никто не успел
    return Outcome.retryNeeded();                // оптимизм: повтор всей транзакции
// баланс: buyerWallet.compareAndSet(balance, balance - cost)
// зачисление продавцу коммутативно -> CAS крутим на месте, конфликта нет
```

Ровно `Transactions.buyCas()` / `setPriceCas()` / `cancelCas()`. Ключевое: CAS по ссылке работает
потому, что `LotV` — immutable record, а `version` растёт на каждое изменение. Наивная стратегия
тот же контейнер портит вызовом `ref.set()` (строка с `// РИСК` в `Transactions.buy`).

### volatile: видимость ≠ атомарность

```java
// server/model/Hazard.java
private static volatile long micros = 150;       // все потоки увидят новое значение

// но volatile НЕ чинит check-then-act:
private volatile long balance;
if (balance >= cost) {        // чтение 1
    balance = balance - cost; // чтение 2 + запись: между ними пролезает другой поток
}
```

`volatile` гарантирует только корректную видимость и запрет переупорядочивания одиночных
операций. Атомарность составных последовательностей — только замок или CAS. Счётчики в
`Counters.java` — вообще `LongAdder`, чтобы сам измерительный прибор не добавлял «скрытый глобальный
замок» на счётчик.

### Condition / wait-notify — где пригодилось бы

```java
Condition restocked = lock.newCondition();
lock.lock();
try {
    while (lot.stock() < qty)          // обязательно while, не if (spurious wakeup)
        restocked.await(timeout, MILLIS);
    /* покупка */
    restocked.signalAll();             // продавец доложил товар
} finally { lock.unlock(); }
```

В лабе не реализовано: вместо «ждать своего лота на Condition» клиент получает 503 `BUSY` и
ретраит по `RetryPolicy`. Это честный вариант со звёздочкой для `queue`/`locks`: парковка
покупателя до пополнения стокa. `wait()/notify()` — то же на мониторе `synchronized`.

### ThreadLocal — почему не спасает

```java
private static final ThreadLocal<Long> myBalance = ThreadLocal.withInitial(() -> 0L);
```

Гонка возникает **между** потоками на **общем** ресурсе; ThreadLocal делает копию на поток, то есть
вообще убирает взаимное исключение, но не общую задачу. Каждый поток со своим «кошельком» — это не
биржа, а расхождение учёта. Где ThreadLocal уместен: MDC/логи, id транзакции, форматтеры — состояние,
которое по определению не разделяют.

### Single-thread executor / актор

```java
Executor actor = new ThreadPoolExecutor(1, 1, 0L, MILLIS,
        new ArrayBlockingQueue<>(512),    // ограниченная! иначе OOM
        threadFactory, new AbortPolicy());
Future<Call> f = actor.submit(() -> Transactions.buy(...));
try {
    return f.get(2000, MILLIS);           // ждём результат с таймаутом
} catch (RejectedExecutionException e) {  // очередь забита
    return Call.fail(503, Call.Reason.QUEUE_FULL, null);   // backpressure
}
```

Это `QueueActorEngine`: вопрос «кто изменяет лот» решён архитектурно, а не синхронизацией —
мутатор ровно один, замков нет, гонок нет. Родственники в проде: event loop (Node, Swing,
`Dispatchers.Main`), Akka-актор, партиционированный консьюмер Kafka. Плата — throughput одной
очереди и латентность; в проде ответ обычно асинхронный (callback / second topic), а не `future.get`.

## 3. Что именно ломается и как это называется

- **Check-then-act (TOCTOU)** — «проверил, что хватает → записал», между шагами другой поток меняет
  данные. Точка `B:check-then-act` в `Transactions.buy` (`if (balance < cost)` … `buyerWallet.set`).
  Следствие: `OVERSELL` (продано больше, чем было) и `NEGATIVE_BALANCE` из `Invariants`.
  Лечение: весь цикл «read-check-write» под одним замком либо под CAS.
- **Lost update** — два потока посчитали новое состояние от одного устаревшего чтения, второй запись
  затёр первую. Строка `ref.set(next); // РИСК: set вместо CAS` в `Transactions.buy`. Оракул:
  `LOST_UPDATE` (подтверждено N записей, `version`-сумма меньше) и `LOST_UNITS` (`stock+sold ≠ initial`).
- **Dirty read (грязное чтение)** — снимок видит промежуточное состояние: деньги списаны у покупателя
  и ещё не зачислены продавцу (точка `C:split-transfer`) → `MONEY_LOST`/`MONEY_CREATED` в
  `Invariants`. Поэтому `snapshot()` — часть контракта стратегии (`ExchangeEngine` javadoc, п.4).
- **Non-repeatable read** — повторное чтение в рамках одной операции даёт другое значение: к моменту
  проверки `lot` устарел (точка `A:read`). Это не «баг БД», а нормальное имя гонки в памяти.
- **Phantom (фантом)** — в обход `listLots()`/снимка посередине попал новый лот (`createLot` в
  `Book.order` — `CopyOnWriteArrayList`). Результат: «рваный» список витрины; в `trylock` это
  объявлено допустимым, в снимке — нет.
- **Deadlock** — 4 условия Коффмана: взаимное исключение, удержание-и-ожидание, отсутствие
  вытеснения, циклическое ожидание. `DeadlockEngine` строит цикл «лот↔кошелёк». Мы ломаем:
  **циклическое ожидание** — глобальный порядок захвата (`TwoLevelLockEngine.orderedLocks`,
  `ShardedTryLockEngine.snapshot` берёт шарды по возрастанию индекса) и/или
  **отсутствие вытеснения** — `tryLock(timeout)` (`exchange.deadlock-escape=true`) имитирует
  принудительный отпуск. Диагностика: `GET /api/lab/threads` (`findDeadlockedThreads`).
  Помнить: deadlock не бросает исключений — молча висят потоки Tomcat (пул 32).
- **Livelock и retry storm** — работа есть, прогресса нет: на `--scenario=hot` все покупатели
  одного лота бесконечно проигрывают CAS. Видно по `conflicts`/`retries` в `Counters`. Меры:
  лимит попыток (`optimistic-retries`, затем 409 `CONFLICT`), экспоненциальный backoff в
  `OptimisticCasEngine.retryLoop` и джиттер в `RetryPolicy.jittered`.
- **Convoy effect (конвой)** — при глобальном замке (`sync`) все клиенты едут со скоростью самой
  медленной критической секции; одна медленная покупка задерживает всю очередь. Усилитель —
  `hazard-micros` внутри секции.
- **Starvation / fairness** — нечестный замок может вечно пропускать одного ожидающего; ручка
  `exchange.fair`. Отдельный вид — writer starvation у нечестного `ReentrantReadWriteLock.
- **Lock hold time поверх I/O** — держать замок на время сети/БД — главный антипаттерн лабы:
  `Hazard`-точки стоят ВНУТРИ секции `sync` именно чтобы вы это увидели в цифрах. Детектор —
  `maxHoldMicros` в `Counters`. Правило: под замок — только мутацию памяти, I/O — до или после.
- **Granularity (гранулярность)** — замок «по лоту» не защищает кошелёк: транзакция задевает лот +
  покупателя + продавца, и блокировать надо **множество ресурсов транзакции**, а не один объект
  (ловушка `ShardedTryLockEngine`, «самая частая ошибка в реальных ревью»). Но и слишком
  крупно — это `sync`: сериализуется то, что не конкурирует.
- **Декомпозиция и глобальный порядок** — много мелких замков даёт параллелизм, но порождает
  deadlock-риск; компенсируется единым детерминированным порядком захвата (+ `distinct()` на
  случай лота, принадлежащего тому же покупателю).
- **Backpressure и отказ вместо очереди** — ждать замок бесконечно = занимать соединение Tomcat
  вечно. Поэтому 503 с различимой причиной: `BUSY` (tryLock), `OVERLOADED` (семафор),
  `QUEUE_FULL` (забитая очередь актора, `AbortPolicy`). Клиент с `RetryPolicy` отрабатывает;
  запрос, простоявший лишнее в очереди, уже не нужен (штраф платим один раз — отказом).

## 4. Как выбирать стратегию

| Профиль нагрузки | Куда смотреть | Почему |
|---|---|---|
| Много разных лотов, конфликты редки | `optimistic`, `trylock` | Каскад CAS почти не срабатывает; шарды дают масштабирование по числу лотов |
| Один горячий лот (`--scenario=hot`) | `queue`, `locks`, `sync` | `optimistic` уходит в retry storm; очередь хотя бы честная и наблюдаемая |
| Доминирующие чтения (`--read-share=0.8`, сценарии readonly/reads) | `rw` | Читатели параллельны; но снимок — под writeLock |
| Низкая латентность, отказ от BUSY нежелателен | `locks`, `queue` | Упорядоченный захват дороже, но почти без отказов — клиенту не нужен retry-код |
| Клиенты готовы ретраить (есть `RetryPolicy`) | `trylock`, `optimistic` | Дешевле на широкой нагрузке, цена — 503 `BUSY` / 409 `CONFLICT` + backoff |
| Нужен честный порядок «как в кассе» | `queue` | Один поток = линейная история; согласованный снимок бесплатно |
| Ограничить внешний ресурс (платёжный шлюз, пул соединений) | `semaphore` | Это про admission control, НЕ про корректность |
| Нужна гарантия любой ценой, простейший код | `sync` | Корректно на 100%, throughput = 1/критическая секция |

Два orthogonal среза, которые спрашивают на защите:

- **Сколько инстансов сервиса?** Все замки и семафоры Java живут внутри одного JVM. За N инстансами
  `sync`/`trylock`/`locks`/`rw`/`queue` защищают только «свой» процесс. Следующий шаг (в лабе НЕ
  реализован): распределённые замки — Redis/Redisson `RLock` (с watchdog), Zookeeper/Curator
  InterProcessMutex (эфемерные sequential-узлы), ShedLock для «запуститься на одном кроне»;
  либо опускать взаимное исключение в БД — `SELECT ... FOR UPDATE`; либо переезжать на оптимизм —
  `@Version` в JPA/Hibernate и `UPDATE ... WHERE version = ?`: это ровно `Transactions.buyCas`
  на другом уровне стека (см. javadoc `OptimisticCasEngine`).
- **Согласованность или доступность?** `sync`/`locks`/`queue` выбирают сериализацию (латентность);
  `trylock`/`semaphore`/`optimistic` выбирают отказ с различимой причиной — и обязывают клиента
  ретраить по `core/http/RetryPolicy.java` (BUSY — перечитать и повторить, CONFLICT — перечитать
  версию, TERMINAL-бизнес-отказы не ретраятся).

## 5. Частые ошибки на защите

1. **«Мы используем ConcurrentHashMap, значит всё потокобезопасно».** Он атомарен на ОДНУ свою
   операцию; транзакция биржи — цепочка вызовов («прочитал лот → списал → начислил»). Прямое
   опровержение — `none`: состояние в `ConcurrentHashMap`, данные порчены (javadoc `Book.java`).
2. **«synchronized на методе — это атомарно на всё приложение».** Монитор действителен только внутри
   одного JVM и только для тех, кто берёт ТОТ ЖЕ объект; `snapshot()`/`listLots()` без замка читают
   параллельно «защищённым» записям. На двух инстансах — не защищает вовсе.
3. **«Достаточно ретраить».** Ретраи не превращают безусловный `ref.set()` в CAS: та же запись
   повторится поверх. А на горячем ресурсе ретраи без лимита и backoff — это livelock
   (`optimistic` на `--scenario=hot`). Ретраит — часть протокола, а не замена синхронизации.
4. **«Семафор гарантирует корректность».** Он гарантирует только «не больше N одновременно».
   Стратегия `semaphore` при permits>1 даёт те же нарушения, что `none`, но реже — самый опасный
   вид бага («тесты зелёные три месяца»).
5. **«Чтения всегда можно не блокировать».** Одиночное поле — да (`getLot` в `trylock`).
   Согласованный снимок нескольких полей — нет: `snapshot()` в `rw` берёт writeLock, `sync` берёт
   global lock, `queue` кладёт снимок в очередь. Иначе `MONEY_LOST` из-за денег «в полёте».
6. **«Если у каждого объекта свой замок — всё в порядке».** Замок по лоту не закрывает кошелёк
   покупателя, воюющего за два лота (`trylock`, NEGATIVE_BALANCE). Блокировать надо множество
   ресурсов транзакции, в едином порядке.
7. **«В логах нет исключений — значит гонок нет».** `BrokenEngine` не бросает ничего. Правильность
   конкурентного кода измеряется инвариантами (`core/check/Invariants.java`), а не stacktrace'ами.
8. **«ReadWriteLock всегда быстрее synchronized».** Только при доле чтений выше порога; при сплошной
   записи — тот же результат плюс накладные расходы (javadoc `ReadWriteEngine`, п.2).
9. **«Fair-замок чинит проблему очереди».** Он чинит starvation и платит throughput'ом. Очередь как
   таковая остаётся: convoy в `sync` (fair=true!) виден в колонке p95.
10. **«volatile/i++ достаточно для счётчика»** — видимость — это не атомарность
    read-modify-write. В лабе счётчики сидят на `LongAdder`/`AtomicLong` именно поэтому
    (`server/stats/Counters.java`).
11. **«Deadlock мы бы заметили по ошибке в логах»** — он не бросает исключений; увидели бы только
    нулевой throughput и таймауты клиентов. Инструмент: `GET /api/lab/threads`.
