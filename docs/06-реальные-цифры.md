# Реальные прогоны: что получилось на машине преподавателя

Это не «ожидаемые результаты из головы», а расшифровка живых прогонов этого проекта.
Цифры переснимались на: **AMD Ryzen 5 5600G (12 логических), 32 ГБ, Windows 10 Pro,
JDK 21.0.9, Spring Boot 3.5.13**. На другой машине абсолютные числа будут другими
(разброс между прогонами на одном железе — до ±40%), **относительная картина та же**,
и именно она предмет разговора на практике.

Как переснять самому:

```bat
java -jar lab-harness/target/lab-harness-1.0.0.jar --ops=40 --seller-ops=12 --csv=out/A-mixed.csv
java -jar lab-harness/target/lab-harness-1.0.0.jar --ops=40 --seller-ops=10 --scenario=hot --pick-mode=min --csv=out/B-hot.csv
java -jar lab-harness/target/lab-harness-1.0.0.jar --ops=40 --seller-ops=10 --read-share=0.7 --pick-mode=random --csv=out/C-reads.csv
mvn -pl exchange-server -am test -Dtest=ReadWriteMicroBenchmarkTest -Dsurefire.failIfNoSpecifiedTests=false
:: последний перезаписывает exchange-server/target/micro-bench.txt
```

Расшифровка колонок: `ops/s` — применённые (успешные) операции в секунду, `p95чт/p95зап` —
95-я перцентиль задержки чтения и записи **отдельно** (усреднять их нельзя: чтений больше,
они дешевле, и общая медиана прячет боль записей), `busy` — 503 от конкурентности,
`retries` — повторы CAS внутри сервера, `затёрто` — подтверждённые записи цены, которые
исчезли (детектор клиента-продавца).

## Прогон A. Обычная витрина: 12 лотов, 12 клиентов, смешанный профиль

| стратегия | инварианты | ops/s | p95чт, мс | p95зап, мс | busy | conflict | retries | maxHold, мкс | затёрто |
|---|---|---|---|---|---|---|---|---|---|
| `none` | **OVERSELLx294, MONEY_CREATEDx1, LOST_UPDATEx193** | 918 | 2.6 | 10.0 | 0 | 0 | 0 | 0 | 3 |
| `semaphore` | **OVERSELLx209, MONEY_CREATEDx1, LOST_UPDATEx132** | 779 | 0.8 | 17.5 | 0 | 0 | 0 | 5978 | 3 |
| `optimistic` | OK | 702 | 1.2 | 31.5 | 0 | 30 | **789** | 34480 | 0 |
| `trylock` | **MONEY_CREATEDx1** | 486 | 0.9 | 43.9 | 23 | 0 | 0 | 6541 | 0 |
| `locks` | OK | 311 | 6.7 | 60.8 | 10 | 0 | 0 | 65704 | 0 |
| `rw` | OK | 201 | 36.7 | 71.6 | 29 | 0 | 0 | 5996 | 0 |
| `sync` | OK | 201 | 49.7 | 70.5 | 0 | 0 | 0 | 5991 | 0 |
| `queue` | OK | 199 | 1.2 | 67.9 | 0 | 0 | 0 | 69019 | 0 |

Что из этой таблицы следует проговаривать:

1. **Наивная реализация не «работает быстрее» — она работает дешевле для вас и дороже для бизнеса.**
   918 ops/s против 201 у `sync`, и при этом 294 перепроданные единицы и 193 потерянных
   обновления на прогоне из ~430 операций: это почти половина подтверждённых записей,
   которых в итоге нет в данных. Ни одного исключения, ни одной ошибки в логах.
2. **Цена самой наивной корректности — ~4.5× throughput.** Это скучный ответ; дальше
   таблица интересна: `trylock` даёт 2.4× к `sync`, оставаясь корректной по складу.
3. **`trylock` — единственная строка, где нарушение одного класса есть, а другого нет**:
   склад чист, касса сломана. Ключ блокировки выбран по лоту, а транзакция задевает
   кошелёк покупателя. Это центральный момент всей практики.
4. **`semaphore` не чинит ничего** — тот же набор нарушений, просто реже
   (и `затёрто=3` против `3` у `none`, то есть даже детектор продавца почти не отличается).
   Ограничение одновременности и атомарность — разные оси.
5. **`optimistic` самая быстрая из корректных и самая «шумная» внутри**: 789 повторов CAS
   при 366 успешных операциях. Заметная часть работы сервера — работа впустую, и за неё
   заплатит клиент задержкой (p95 записи 31 мс против 10 мс у наивной).
6. **`queue` платит не throughput'ом, а хвостом и памятью**: `ops/s` как у `sync`,
   `maxHoldMicros` 69 мс (это не удержание замка, а время ожидания в очереди — в этом
   стратегии и смысл), зато `p95чт = 1.2 мс`: чтения идут мимо очереди и почти не страдают.
7. **`rw` и `sync` по записям совпали (201 против 201)** — ожидаемо: запись упирается
   в один и тот же ресурс при любом типе замка. По чтениям различие в этой паре через HTTP
   почти не видно (36.7 против 49.7 мс), а видно его в микро-бенчмарке ниже. Хороший повод
   сказать студентам: «транспорт — тоже часть вашего замера, и он умеет прятать эффекты».
8. `locks` дороже `trylock` по записям (311 против 486) — цена того, что мы берём три замка
   вместо одного и держим их дольше (`maxHoldMicros` это честно показывает: 65 мс — это
   очередь в прогоне, а не «мы долго думали»).

## Прогон B. Один горячий лот (`--scenario=hot --pick-mode=min`)

| стратегия | инварианты | ops/s | p95зап, мс | busy | conflict | retries |
|---|---|---|---|---|---|---|
| `none` | OVERSELLx413, MONEY_CREATEDx1, LOST_UPDATEx370 | 1147 | 9.3 | 0 | 0 | 0 |
| `semaphore` | OVERSELLx413, MONEY_CREATEDx1, LOST_UPDATEx303 | 781 | 18.7 | 0 | 0 | 0 |
| `optimistic` | OK | **397** | 32.4 | 0 | **134** | **1615** |
| `locks` | OK | 210 | 63.0 | 43 | 0 | 0 |
| `rw` | OK | 204 | 69.0 | 20 | 0 | 0 |
| `queue` | OK | 203 | 68.0 | 0 | 0 | 0 |
| `sync` | OK | 203 | 72.8 | 0 | 0 | 0 |
| `trylock` | OK | **219** | 46.4 | **96** | 0 | 0 |

Здесь ломается интуиция «декомпозиция замка всегда лучше»:

* `trylock` упал с 486 до **219 ops/s** и выдал 96 отказов: декомпозировать нечего,
  весь трафик на одном лоте, замок по лоту превращается в глобальный — только с отказами
  вместо ожидания. И именно здесь обязан уметь повторять клиент.
* `optimistic` потерял почти половину скорости прогона A и ушёл в 1615 повторов:
  конкуренты всё время затирают друг друга, каждый проигравший начинает заново.
  Это пограничье между «оптимистично» и **livelock** — работа есть, прогресса почти нет.
* `MONEY_CREATED` у `trylock` на этом прогоне **исчез** — не потому что стратегия стала
  лучше, а потому что все клиенты собрались в одном лоте, то есть в одном шарде, и кошелёк
  случайно оказался под тем же замком. Живая иллюстрация того, как «не воспроизводится»
  маскирует «не починено».

## Прогон C. Много чтений (`--read-share=0.7 --pick-mode=random`)

| стратегия | ops/s (записи) | p95чт, мс | p95зап, мс | инварианты |
|---|---|---|---|---|
| `trylock` | 522 | **0.75** | 24.9 | MONEY_CREATEDx1 |
| `semaphore` | 473 | 0.81 | 17.4 | OVERSELLx…, LOST_UPDATE… |
| `optimistic` | 463 | 2.6 | 23.2 | OK |
| `none` | 437 | 4.4 | 15.0 | MONEY_CREATEDx1, LOST_UPDATEx34 |
| `locks` | 344 | 4.7 | 42.5 | OK |
| `sync` | 214 | 28.8 | 52.9 | OK |
| `rw` | 203 | 30.1 | 53.6 | OK |
| `queue` | 186 | **1.37** | 67.3 | OK |

Честный вывод, который надо умеить произнести вслух: **в рамках HTTP-прогона `rw` не обошёл
`synchronized`** — 190−215 записей/с держат замок занятым почти всё время, и читателям некуда
влезть при любом типе замка. Зато `queue` и `trylock` дают дешевые чтения (1.4 и 0.75 мс),
потому что чтения вообще не идут через их узкое место.

Если студент утверждает, что «ReadWriteLock всё равно быстрее» — попросите его снять
это без транспорта:

## Микро-бенчмарк стратегий напрямую (без HTTP, `hazard=0`)

Из `exchange-server/target/micro-bench.txt`, 32 потока на чтения, 8 на записи, 96 лотов:

| стратегия | чтений/с | записей/с |
|---|---|---|
| `none` | 359 710 | 219 043 |
| `sync` | **84 512** | 68 333 |
| `trylock` | 380 977 | **477 412** |
| `rw` | 762 620 | 192 066 |
| `optimistic` | 811 314 | 376 294 |
| `queue` | 954 764 | 151 796 |
| `locks` | 970 629 | 166 029 |

Вот теперь видно всё, о чём говорила таблица A, но без шума транспорта:

* чтение под глобальным замком — **в 9 раз** медленнее, чем под `ReadWriteLock`
  (84k против 762k) и в 11 раз медленнее, чем в акторе, где чтения вообще не блокируются;
* по записям декомпозиция даёт 7× к глобальному замку (`trylock` 477k против 68k), а
  оптимистичная стратегия — 5.5×;
* **`none` не является самой быстрой по записям** (219k против 477k у `trylock`):
  «мы просто ничего не блокируем» не равно «мы быстры». Потоки выбивают друг друга из кэша
  и затирают записи, часть работы уходит в мусор. Хорошая точка, чтобы похоронить аргумент
  «оптимизируем снятием замков»;
* у `queue`/`locks` чтения максимальны (954k / 970k), а записи средние: ровно то, что
  обещает архитектура с одним потоком-исполнителем и упорядоченным захватом трёх замков.

## Как обращаться с этими числами на практике

1. Не сдавай вывод без прогона на своей машине. Абсолютные цифры поплывут, картина — нет.
2. Один прогон ничего не доказывает: запусти харнес с `--repeat=3` и посмотри разброс
   `ops/s`. Если разброс сопоставим с разницей стратегий — вы спорите о шуме, а не о решении.
3. `hazard-micros` меняет выводы: при `0` гонка воспроизводится реже, при `600`
   становится видно, кто держит замок поверх «медленной работы» (это почти всегда
   антипаттерн, и он стоит отдельного абзаца в отчёте).
4. Сравнивай всегда две колонки одновременно: `инварианты` и `ops/s`. Разговор
   «быстро» без разговора «правильно» — это не инженерный вывод, а выбор бага по вкусу.
5. Если две стратегии в таблице совпали — это не обязательно ошибка измерения: возможно,
   узкое место находится ниже вашего замка (транспорт, сериализация JSON, пул Tomcat).
   Уметь сказать «наш эксперимент эту разницу не разрешает» важнее, чем придумать объяснение.
