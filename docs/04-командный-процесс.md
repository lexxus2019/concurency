# Командный процесс в лабе: роли, контракт, ветки, ревью

Этот файл — про вторую половину темы занятия. Первая половина — «как починить гонку».
Вторая, ради которой лаба и разбита на модули: **починка конкурентности — это решение
команд, а не строчка кода**, потому что оно всегда залезает в чужой модуль.

---

## 1. Распределение ролей (на группу из 3–4 троек)

| команда | владеет | чего хочет | чем мешает другим |
|---|---|---|---|
| **Биржа** | `exchange-server/**` | чтобы состояние не портилось и не зависало | вынуждена менять ответы API (409/503), трогает чужие ожидания |
| **Покупатели** | `buyer-client/**` | минимальную задержку и никаких потерянных заказов | не хочет писать код повторов и передавать `If-Match` |
| **Продавцы** | `seller-client/**` | чтобы её подтверждённые записи не исчезали | хочет условных записей и «отзыва» посреди нагрузки |
| **Все** | `exchange-core/**` (контракт) | стабильный контракт | правка контракта ломает остальных — отсюда и процесс |

Каждая тройка обязана в конце практики ответить не только «что я сделал», но и
**«что я попросил сделать у соседней команды и как мы договорились»**. Это и есть оценка
за командную работу: код можно написать отличный, а результат не принять, потому что
клиент не знает про `409`.

## 2. Почему модули поделены именно так

```
exchange-core     ← НЕТ зависимостей от Spring, только DTO + HttpClient + инварианты
  ↑        ↑        ↑
server     buyer    seller   ← каждый видит контракт, но не видит чужую реализацию
```

Три следствия, которые стоит проговорить на практике:

1. **Клиент физически не может «подсмотреть» состояние сервиса** — только то, что
   сервис решил рассказать. Значит все проверки корректности формулируются как
   наблюдаемые инварианты (`Invariants`), а не как «я знаю, что внутри».
2. **Контракт — единая точка согласия.** В `exchange-core` три осознанных «крючка» под
   конкурентность: `expectedVersion` в запросах, коды `409/503` и
   `Call.Reason` (`BUSY/CONFLICT/OVERLOADED/QUEUE_FULL/TIMEOUT`), и
   `RetryPolicy` на клиенте. Убрать их нельзя, можно только договориться, как они работают.
3. **Сервис выбирает стратегию через реестр, а не через `switch`.** Все реализации
   `ExchangeEngine` собираются Spring'ом в `EngineRegistry`. Покажи студентам разницу:
   при `switch (strategy)` два человека правят одну строку в одном файле и конфликтуют;
   при регистрации бинами они добавляют по файлу и конфликтуют только в `.gitignore`.
   Это самый дешёвый пример того, как архитектура снижает трение в команде.

## 3. Git-сценарий на 15 минут (рекомендую показать вживую)

```bat
scripts\init-git.cmd                     :: репозиторий + первый коммит, если ещё не сделали
git switch -c strategy/sync              :: команда «Биржа», задача 3
git switch -c strategy/trylock           :: другая тройка, задача 4
...
git switch main
git merge strategy/sync
git merge strategy/trylock               :: конфликт? посмотрите где и почему
```

Что обычно конфликтует — и это полезно обсудить:

* `EngineInvariantTest.fullyCleanStrategies()` — обе ветки дописали туда своё имя.
  Разрешение: оба additions, строка объединения списков. Отличный повод сказать про
  «тесты как общий ресурс» и про то, как такую таблицу вести, чтобы она не была точкой
  конфликта (параметризовать списком бинов, а не литералом имён).
* `application.yml` — свойство `exchange.strategy` хочет поставить каждый.
  Правило команды: значение по умолчанию остаётся `none`, переключение — только через API
  или аргумент запуска.
* `exchange-core` — если одна команда решила добавить `requestId` для идемпотентности.
  Это уже RFC: обсуждаем, согласовываем, потом мержим. Здесь стоит задержать группу и
  провести мини-митинг на 5 минут, чтобы они прочувствовали цену.

**Чего специально не происходит:** конфликтов в `engine/`. Если на вашей практике их нет —
это не удача, это архитектурное решение, см. пункт 2.3.

## 4. Ревью-чеклист (то, по чему принимаем чужую стратегию)

Короткий, чтобы проверяющий тройке тройки реально им пользовался:

- [ ] Все мутации состояния проходят через `Transactions.*` — своей «быстрой» логики внутри стратегии нет.
- [ ] Каждый конкурентный отказ различим клиентом: `BUSY`/`CONFLICT`/`OVERLOADED`/`QUEUE_FULL`, а не `500`.
- [ ] Нет `Thread.sleep` как способа «развести потоки по времени» (это не синхронизация, это лотерея).
- [ ] Замок не удерживается дольше, чем нужно: `maxHoldMicros` сопоставим с hazard-точками, а не с таймаутом клиента.
- [ ] Вложенные замки берутся в едином порядке либо с `tryLock(timeout)`.
- [ ] `release()` семафора/`unlock()` — в `finally`; проверено на исключении внутри секции.
- [ ] Чтения согласованы там, где это нужно: одиночный `get` ≠ `snapshot()`.
- [ ] Есть тест/прогон, доказывающий, что нарушения *воспроизводились* до фикса (иначе «стало лучше» не проверить).
- [ ] Изменения в `exchange-core` согласованы со второй и третьей командой (запись в отчёте: кто, что, когда согласовал).

## 5. Как выглядит «готово» (definition of done для одной стратегии)

1. Файл стратегии + имя в реестре, `--only=твоя_стратегия` печатает строку в таблице.
2. Колонка `инварианты` = `OK` на двух профилях нагрузки (`default` и `hot`).
3. В отчёте есть предложение с числом: «мы заплатили за это X% throughput / Y мс p95 /
   Z% отказов busy / доработку клиента на N строк».
4. Соседняя тройка (команда «клиентов») подтвердила, что умеет обращаться с твоими отказами:
   знает, что ретраить, а что нет, и что перечитывать перед повтором.

## 6. Что сказать про «продакшен», чтобы лаба не выглядела игрушкой

* Здесь состояние живёт в одном JVM-процессе. В проде оно в БД/кэше/очереди, и все
  выводы остаются в силе, меняется только механизм: `SELECT … FOR UPDATE`,
  `@Version` (+ ретрай на уровне сервиса), распределённый замок (Redis/Zookeeper) или
  партиционирование в брокере (Kafka по ключу лота = тот же «замок по лоту», только
  размазанный по кластеру).
* Настоящая цена любого распределённого замка — не latency, а «что делать, если
  владелец замка умер с ним в руках»: TTL, fencing токены, идемпотентные операции.
  Это хорошая тема следующего занятия и вариант starred-задания.
* Самое дешёвое решение в проде часто не «какой замок поставить», а **разбить ресурс**:
  своя партиция на лот, свой агрегат на покупателя, одна строка на одну операцию вместо
  «перепиши весь объект». Формулировка, которую стоит потребовать от студентов в отчёте:
  «мы можем вообще не спорить за ресурс, если изменим модель данных».
