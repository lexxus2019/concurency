# Биржа: несколько команд — один service (лаборатория по конкурентному доступу)

Репозиторий: <https://github.com/lexxus2019/concurency> · CI: `.github/workflows/ci.yml` ·
сдача практики идёт через ветку, PR и ревью соседней тройкой — см. `docs/08-github-процесс.md`.

Учебный проект для практики по теме **«программирование в команде»**. Три независимых
процесса (сервис биржи, клиент-покупатель, клиент-продавец) работают с одним общим
состоянием, и студент на своих руках видит, как это ломается, — а потом чинит это
девятью разными способами и измеряет цену каждого способа.

Тема занятия — не «как написать `synchronized`», а то, с чем команда сталкивается в
реальности: **несколько сервисов конкурентно пишут в одни и те же ресурсы**. Поэтому
лаба устроена как конфликт: у каждого участника свой код, свои интересы, и договориться
приходится про контракт, а не про синтаксис.

---

## 1. Быстрый старт (Windows, JDK 21 + Maven 3.9)

```bat
:: 0. собрать всё (первый раз ~2 минуты, дальше кэш)
mvn -DskipTests package

:: 1. запустить биржу (окно 1)
scripts\run-server.cmd

:: 2. запустить покупателя (окно 2)
scripts\run-buyer.cmd

:: 3. запустить продавца (окно 3)
scripts\run-seller.cmd

:: 4. одна команда, которая прогоняет ВСЕ стратегии и печатает таблицу
scripts\harness.cmd
```

Если хочется без скриптов:

```bat
java -jar exchange-server/target/exchange-server-1.0.0-exec.jar
java -jar buyer-client/target/buyer-client-1.0.0.jar  --server=http://localhost:8080
java -jar seller-client/target/seller-client-1.0.0.jar --server=http://localhost:8080
java -jar lab-harness/target/lab-harness-1.0.0.jar --csv=out/results.csv
```

Проверить, что среда живая:

```bat
curl http://localhost:8080/api/lab/strategies
curl http://localhost:8080/api/lab/state
```

## 2. Сценарий на 25 секунд (то, что препод показывает в начале)

```bat
java -jar lab-harness/target/lab-harness-1.0.0.jar --ops=40 --seller-ops=12 --csv=out/first.csv
```

Через полминуты на экране таблица, в которой у наивной реализации стоит
`OVERSELL`, `MONEY_CREATED` и `LOST_UPDATE`, у `synchronized` — `OK`, но в 3−4 раза
меньше `ops/s`, а у `trylock` — `OK` по складу и `MONEY_CREATED` по кассе. Дальше
вся практика — это вопросы «почему» и «что делать».

## 3. Что здесь что

```
exchange-core/        контракт: DTO, HTTP-клиент, проверки инвариантов, RetryPolicy
                      ← этот модуль «общий», его правят только по договорённости
exchange-server/      биржа: Spring Boot + 9 стратегий синхронизации (engine/**)
buyer-client/         клиент-покупатель: читает витрину, покупает, повторяет отказы
seller-client/        клиент-продавец: выставляет лоты, уценивает, ОТЗЫВАЕТ лоты и
                      детектирует потерянные подтверждённые записи
lab-harness/          прогонощик: одинаковая нагрузка на каждую стратегию + таблица
docs/                 методичка, задания, шпаргалка, вопросы, реальные цифры
scripts/              cmd-файлы для аудитории, чтобы не вспоминать флаги на глаз
out/                  результаты прогонов (csv/логи), не жалко удалять
```

Ключевой файл проекта — `exchange-server/src/main/java/ru/lab/concurrent/server/engine/Transactions.java`:
вся бизнес-логика биржи **без единой синхронизации**, с четырьмя помеченными точками
риска. Стратегии этот файл не трогают — они только оборачивают его. Так устроено
нарочно: спорить мы будем об обёртке, а не о предметной области.

## 4. Девять стратегий (переключаются на живом сервисе)

| ключ `exchange.strategy` | что это | почему это интересно на практике |
|---|---|---|
| `none` | наивная запись «прочитал-посчитал-записал» | стартовая точка лабы; воспроизводит все аномалии |
| `sync` | один замок на весь сервис | корректно и дорого; ещё и чтения в очереди |
| `trylock` | замок на шард лота + `tryLock(timeout)` → 503 | декомпозиция + отказ вместо зависания; **дыра: кошелёк не защищён** |
| `locks` | замки лота+покупателя+продавца в едином порядке | как чинится дыра предыдущей стратегии |
| `rw` | `ReadWriteLock` | где выигрывают чтения (и где нет) |
| `optimistic` | `version` + CAS + повторы | цена конфликтов, требует `If-Match` у клиента |
| `queue` | очередь + один поток (актор) | корректность без замков вовсе, backpressure |
| `semaphore` | `Semaphore(permits)` | **задание с подвохом**: ограничить ≠ атомарно |
| `deadlock` | два замка в разном порядке | как выглядит взаимоблокировка и чем она кончается |

Переключение без рестарта (все стратегии работают с одной и той же книгой):

```bat
curl -X POST "http://localhost:8080/api/lab/strategy?name=rw"
curl http://localhost:8080/api/lab/strategy
```

Важный побочный эффект, о котором студенты забывают: **смена стратегии не чинит уже
испорченные данные**. После `none` нарушения висят в состоянии до `POST /api/lab/reset`
— отдельный вывод про то, что миграция данных и фикт кода это две разные задачи.

## 5. Конфигурация (`exchange-server/src/main/resources/application.yml`)

| свойство | дефолт | зачем крутить |
|---|---|---|
| `exchange.strategy` | `none` | активная стратегия при старте |
| `exchange.hazard-micros` | `150` | длина «медленной работы» внутри критической секции; `0` = гонку надо ловить долгим прогоном |
| `exchange.lock-timeout-ms` | `40` | когда `tryLock` сдаётся и отдаёт 503 BUSY |
| `exchange.lock-shards` | `64` | гранулярность декомпозиции замка |
| `exchange.fair` | `false` | честный замок: меньше starvation, ниже throughput |
| `exchange.optimistic-retries` | `8` | сколько раз CAS-стратегия повторяет транзакцию |
| `exchange.queue-capacity` / `queue-timeout-ms` | `512` / `2000` | глубина очереди актора и ожидание результата |
| `exchange.permits` | `4` | ёмкость семафорной стратегии |
| `exchange.deadlock-escape` | `false` | `true` = спасение через `tryLock`, `false` = вечное зависание |

Единственное свойство, которое стоит менять на ходу ради учебника, — `hazard-micros`:

```bat
curl -X POST "http://localhost:8080/api/lab/hazard?micros=600"
```

## 6. Как добавить свою стратегию (это и есть основное задание)

1. Создай пакет/класс, например `engine/mylock/MyEngine.java`, унаследуй `AbstractEngine`.
2. Реализуй `name()`, `title()`, `howItWorks()`, `buy()`, `setPrice()`, `cancel()`,
   по желанию `listLots()`/`snapshot()`. Внутри — `guardedTx(мойЗамок, таймаут, () -> Transactions.buy(...))`.
3. Поставь `@Component` — больше делать ничего не нужно: `EngineRegistry` собирает все
   бины `ExchangeEngine` в реестр сам, поэтому **две команды, принёсшие по стратегии,
   не правят один и тот же файл** и не ловят merge conflict в `switch`.
4. Проверь `mvn -pl exchange-server -am test` — тест `EngineInvariantTest` параметризован
   и сам подхватит новую стратегию, если ты добавишь её имя в `fullyCleanStrategies()`.
5. Запусти харнес со своей стратегией: `--only=none,sync,my-thing`.

## 8. Чего здесь сознательно нет

* **Базы данных.** Всё состояние в памяти одного процесса: чтобы студент боролся с
  конкурентностью, а не с Hibernate. Переход к `@Version`, `SELECT … FOR UPDATE` и
  распределённому замку описан в `docs/04` как «следующая лаба» и как задание со звёздочкой.
* **Настоящего брокера.** Очередь сделана single-thread executor'ом. Тот же актор-паттерн,
  но без Zookeeper на ноутбуках студентов; замена на ActiveMQ `vm://` / Kafka-партицию —
  starred-задание.
* **Безопасности и тестового покрытия «как в проде».** Это учебный полигон:
  один инстанс, никакой аутентификации, id в открытом виде.
